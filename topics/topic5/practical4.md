# Практична 4. Архітектурний дизайн і каркас проєкту

На попередньому етапі ви сформували вимоги до MVP: шлях користувача, користувацькі історії та критерії приймання. Тепер час перейти від опису поведінки продукту до його технічного проєктування. 

Головна пастка цього етапу — одразу кинутися писати код фіч або сліпо попросити ШІ «зробити бекенд». Без чітких правил і домовленостей це призведе до хаосу, несумісних типів даних і зламаної структури. На цьому кроці за допомогою генеративного ШІ ви зафіксуєте технічні рішення під реальні ресурси своєї команди, спроєктуєте контракти (модель даних та API/інтерфейси), налаштуєте правила для ШІ в репозиторії та піднімете перший живий каркас застосунку — **«крокуючий скелет» (Walking Skeleton)**.

> **Важливе правило:**  
> **НА ЦЬОМУ ЕТАПІ МИ НЕ ПИШЕМО БІЗНЕС-ЛОГІКУ ФІЧ!**  
> Ви не реалізуєте користувацькі історії в коді зараз. Ваша мета — створити порожній, але живий наскрізний каркас, який успішно збирається, запускається однією командою та має визначені правила взаємодії. Реалізацією самих історій за допомогою ШІ в IDE ви займатиметеся на наступних етапах.

---

### Що потрібно зробити (Покрокова інструкція)

1. **Провести технічний аналіз вимог і знайти прогалини (Requirements Digest):**
   * Завантажити свої вимоги з КТ-3 у мовну модель (використавши її як системного аналітика).
   * Виявити ключові сутності системи, їхні життєві цикли (переходи між станами, наприклад: *Чернетка ➔ Опубліковано ➔ Закрито*), суворі бізнес-правила й заборони (чого системі робити категорично не можна), а також зафіксувати технічні припущення для MVP (як працює авторизація, формат ідентифікаторів тощо).
   * Зберегти використаний промпт.

2. **Зафіксувати архітектурні рішення (ADRs):**
   * Сформулювати для ШІ реальні обмеження своєї команди: склад (4–6 людей), дедлайн семестру, локальний запуск, нульовий бюджет, наявний досвід зі стеком.
   * За допомогою ШІ розглянути альтернативи та оформити архітектурні рішення (Architecture Decision Records — ADR) під ключові вузли системи:
     * Загальна структура репозиторію (наприклад, монорепозиторій чи окремі папки);
     * Стек для інтерфейсу користувача (UI);
     * Стек для рівня бізнес-логіки (Backend / Сервіси);
     * Спосіб збереження даних (реляційна чи документоорієнтована база даних, ORM тощо);
     * Інші важливі рішення за потреби вашого проєкту (наприклад, спосіб автентифікації).
   * Зберегти використаний промпт.

3. **Спроєктувати технічні контракти (Дані та API / Інтерфейси):**
   * **Схема збереження даних:** описати структуру таблиць/колекцій, типи полів, зв'язки між ними, первинні ключі та обмеження унікальності під історії вашого MVP.
   * **Контракти взаємодії (API / точки входу):** описати специфікацію ендпоінтів або інтерфейсів взаємодії між клієнтом і сервером для історій MVP (шляхи, методи, вхідні дані, обов'язкові коди статусів успіху й типових помилок).
   * **Єдиний формат помилок:** зафіксувати стандартизовану структуру відповіді при виникненні будь-якої помилки в системі.
   * Зберегти використаний промпт.

4. **Налаштувати інструкції для ШІ-асистента в репозиторії (AI-Harness):**
   * Створити в корені репозиторію файл конфігурації для роботи мовних моделей (наприклад, `CLAUDE.md`, `.github/copilot-instructions.md` або `.cursorrules` — залежно від обраного командою інструменту).
   * Описати в ньому: коротку суть проєкту, команди збірки, запуску та тестування, структуру папок, правила кодогенерації та чіткі інженерні заборони (наприклад: *«Не вигадуй поля сутностей самостійно — перевіряй контракти в docs/»*).

5. **Ініціалізувати та запустити початковий каркас (Крокуючий скелет/Walking Skeleton):**
   * За допомогою ШІ згенерувати початкову структуру папок вашого проєкту (рівень UI + рівень логіки/API + рівень даних або спільних моделей).
   * Забезпечити зв'язок між шарами без написання логіки:
     * Сервер/бекенд запускається і має простий ендпоінт перевірки здоров'я (наприклад, `GET /api/health` повертає статус `200 OK` або тестове повідомлення);
     * Клієнтська частина (UI) відкривається у браузері або запускається як застосунок (показує базову стартову сторінку-заглушку з назвою проєкту та назвами майбутніх екранів);
     * База даних або сховище підключається (створено тестове з'єднання або застосовано початкову порожню схему/міграцію).
   * Проєкт повинен запускатися локально **1–2 простими командами**, описаними у вашому головному `README.md`.
   * Зберегти використаний промпт.

6. **Оформити репозиторій та здати завдання:**
   * Закомітити всю документацію, правила для ШІ та згенерований каркас коду.
   * Надіслати посилання на GitHub-репозиторій у полі відповіді до завдання на DistEdu до початку практичної зустрічі.

7. **Взяти участь у практичній зустрічі (20 хв):**
   * **Перші 3 хвилини — Live Demo каркаса (команда демонструє екран):**
     1. Запуск проєкту з чистого терміналу за 1–2 командами;
     2. Демонстрація відповіді тестового ендпоінта перевірки зв'язку (`/api/health` або аналог);
     3. Демонстрація відкритого інтерфейсу (сторінка-заглушка);
     4. Короткий показ файлу інструкцій для ШІ (`CLAUDE.md` чи аналог) та озвучення 1 ключового архітектурного рішення.
   * **Решта часу (17 хв):** інженерне рев'ю технічного дизайну з викладачем (відповідність контрактів історіям MVP, адекватність вибору технологій під дедлайни, зворотний зв'язок).

---

### Що має бути в репозиторії (Артефакти)

1. **Папка технічної документації `docs/`:**
   * Документ технічного аналізу вимог (сутності, життєві цикли зі зміною станів, заборони та припущення);
   * Папка `docs/adr/` із зафіксованими архітектурними рішеннями команди;
   * Технічні контракти: схема збереження даних та специфікація API/інтерфейсів із єдиним форматом помилок.
2. **Файл інструкцій для ШІ в корені репозиторію:**
   * `CLAUDE.md` (або `.github/copilot-instructions.md`, `.cursorrules`).
3. **Робочий код каркаса (Walking Skeleton):**
   * Файлова структура проєкту (UI, серверна частина, схеми даних);
   * Оновлений кореневий `README.md` із чіткими командами локального запуску та перевірки.
4. **Папка `prompts/` (4 обов'язкові файли):**
   * `4.1_requirements_digest.md` — аналіз вимог, виділення сутностей, станів та обмежень;
   * `4.2_adr_generation.md` — вибір та обґрунтування технологічного стеку під обмеження;
   * `4.3_technical_contracts.md` — проєктування контрактів API та схеми збереження даних;
   * `4.4_scaffolding_skeleton.md` — генерація файлової структури каркаса та інструкцій для ШІ.

---

### Очікуваний результат
* У репозиторії наявна повна технічна документація (аналіз вимог, ADR, контракти).
* У корені налаштовано файл правил для взаємодії з ШІ.
* Каркас коду без бізнес-логіки успішно збирається і стартує локально.
* Збережено 4 файли промптів у папці `prompts/`.
* Присутність усієї команди на зустрічі та успішне 3-хвилинне живе технічне демо.

### Критерії оцінювання (максимум — 7 балів)
Оцінювання здійснюється за бінарною шкалою (1 бал — виконано, 0 балів — не виконано):

| № | Критерій | 1 бал | 0 балів |
|:---:|---|---|---|
| 1 | **Присутність команди** | Уся команда присутня на зустрічі вчасно. | Відсутній хоча б один учасник команди (без поважної причини). |
| 2 | **Папка prompts/ (4 файли)** | Наявні всі 4 файли (`4.1`–`4.4`) із релевантними інженерними промптами під кожен крок. | Відсутній хоча б один файл, або тексти запитів шаблонні й не відповідають проєкту. |
| 3 | **Аналіз сутностей та обмежень (Digest)** | У документації зафіксовано сутності, їхні життєві цикли (переходи між станами), суворі правила/заборони та припущення до MVP. | Опис сутностей відсутній, не вказано станів або проігноровано обмеження системи. |
| 4 | **Архітектурні рішення (ADRs)** | Зафіксовано обґрунтовані ADR для ключових компонентів системи з урахуванням обмежень команди та порівнянням варіантів. | ADR відсутні, або стек обрано без урахування реальних обмежень (нереалістичні для семестру рішення). |
| 5 | **Контракти API та Схема даних** | Описано специфікацію ендпоінтів/інтерфейсів під історії MVP зі статус-кодами, єдиний формат помилок та схему даних (поля, типи, зв'язки). | Контракти відсутні, не узгоджені з історіями MVP, немає статус-кодів або відсутній формат обробки помилок. |
| 6 | **Інструкції для ШІ (AI-rules)** | У корені наявний конфігураційний файл (`CLAUDE.md` або аналог) з описом проєкту, командами запуску та правилами генерації коду. | Файл правил для ШІ відсутній або містить випадковий, неадаптований під проєкт текст. |
| 7 | **Живе технічне демо каркаса** | Команда наживо запустила проєкт: працює тестовий сервісний ендпоінт перевірки здоров'я та відкривається UI-заглушка. | Каркас не запускається, падає з помилками під час демо, або запуск вимагає складних ручних маніпуляцій. |
