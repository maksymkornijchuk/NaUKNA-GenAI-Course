# Практичне завдання 5: Розробка першого робочого сценарію

У попередньому завданні ви створили «порожній каркас» (Walking Skeleton) вашого проєкту: налаштували репозиторій, зафіксували контракти та правила для ШІ. Тепер час оживити систему та перейти до написання реального коду.

Головна інженерна пастка на цьому етапі — спробувати закодити весь проєкт одночасно. Це неминуче призводить до втрати контексту мовною моделлю, накопичення прихованих багів і непрацездатного продукту. На цьому кроці ви реалізуєте **лише один цілісний сценарій (один Епік або 2–3 пов'язані історії)**, але зробите це наскрізно: *від дій користувача в інтерфейсі ➔ через бізнес-логіку ➔ до збереження даних у сховищі*. 

Розробка ведеться за допомогою ШІ-інструментів безпосередньо в IDE або терміналі, проходить детерміновані перевірки (типи, лінтери) та обов'язкове **код-рев'ю за допомогою ШІ** перед злиттям у головну гілку.

---

### Що потрібно зробити

1. **Обрати один наскрізний сценарій (Епік):**
   * Виберіть із вашого MVP один логічно завершений користувацький сценарій (наприклад: *створення сутності та її відображення у списку*, або *пошук об'єкта та подача заявки/дії*).
   * Не беріть усе одразу. Важливо, щоб обраний сценарій можна було повністю пройти від початку до кінця.

2. **Реалізувати функціонал у новій Git-гілці за допомогою ШІ:**
   * Створіть для задачі окрему гілку (наприклад, `feature/core-flow`).
   * Використовуйте AI-асистента в IDE (Cursor, VS Code, JetBrains) або CLI-агента, спираючись на контекст вашого проєкту (`AGENTS.md`, `CLAUDE.md`, контракти з `docs/`).
   * Реалізуйте всі шари вашого застосунку:
     * **Інтерфейс користувача (UI):** візуальні елементи введення та відображення даних (вебсторінка, екран додатку, десктопне вікно тощо);
     * **Рівень бізнес-логіки:** обробка запитів, валідація, правила системи;
     * **Збереження даних:** реальний запис та читання зі сховища (реляційна чи документоорієнтована БД, локальна база даних тощо). Дані не повинні зникати після перезапуску програми!
   * Збережіть використані запити в папці `prompts/`.

3. **Застосувати детерміновані перевірки (Guardrails):**
   * Переконайтеся, що проєкт збирається без помилок, компілятор/перевірка типів не видає зауважень, а лінтери задоволені.
   * Якщо ШІ згенерував код із синтаксичними чи типізаційними помилками — використайте його ж для швидкого виправлення зауважень терміналу.
   * Збережіть промпти виправлення/рефакторингу.

4. **Провести код-рев'ю за допомогою ШІ (AI Code Review):**
   * Створіть **Pull Request (PR)** у GitHub для влиття вашої гілки в `main`.
   * Проведіть рев'ю коду за допомогою ШІ: це може бути аналіз через GitHub-бота, інтеграція з асистентом у PR або запуск локального ШІ-агента для аудиту `git diff`.
   * ШІ повинен перевірити: відповідність архітектурі, безпеку, обробку помилок і чистоту коду.
   * Внесіть виправлення за суттєвими зауваженнями ШІ.

5. **Злити код у `main` та підготувати демо:**
   * Змерджіть перевірений Pull Request у гілку `main`.
   * Внесіть у `README.md` коротку інструкцію: яку дію виконати, щоб протестувати реалізований сценарій наживо.

6. **Здати роботу на DistEdu:**
   * Надішліть посилання на репозиторій у полі відповіді до завдання на DistEdu до початку практичної зустрічі.

7. **Взяти участь у практичній зустрічі (20 хв):**
   * **Перші 3 хвилини — Live Demo (команда демонструє екран):**
     1. Запуск застосунку наживо;
     2. Проходження реалізованого сценарію через UI (введення даних ➔ реакція системи);
     3. Демонстрація того, що дані реально збереглися в базі / сховищі;
     4. Короткий показ закритого Pull Request у GitHub із коментарями або слідами проведеного ШІ-рев'ю.
   * **Решта часу (17 хв):** інженерне обговорення з викладачем (як організували роботу з ШІ в IDE, які виникли проблеми, як відпрацювало код-рев'ю, зворотний зв'язок).

---

### Що має бути в репозиторії (Артефакти)

1. **Працюючий код у гілці `main`:**
   * Повністю робочий наскрізний сценарій (UI + логіка + персистентні дані).
2. **Закритий (Merged) Pull Request у GitHub:**
   * PR, через який додавався функціонал, із зафіксованими слідами код-рев'ю від ШІ (коментарі, звіт аудиту чи опис врахованих зауважень моделі).
3. **Оновлений `README.md`:**
   * Блок *«Як перевірити перший робочий сценарій»* (короткий покроковий опис для запуску та тесту).
4. **Папка `prompts/` (3 обов'язкові файли):**
   * `5.1_code_generation.md` — запити для генерації коду обраного сценарію в IDE/CLI;
   * `5.2_fixing_and_refactoring.md` — запити для виправлення помилок, типів або узгодження з базою;
   * `5.3_ai_code_review.md` — промпт або правила, за якими ШІ проводив аудит коду перед злиттям.

---

### Очікуваний результат
* Реалізований та працюючий наскрізний функціонал у гілці `main`.
* Наявний закритий PR зі слідами код-рев'ю від ШІ.
* Збережено 3 файли промптів у папці `prompts/`.
* Присутність усієї команди на зустрічі та успішне 3-хвилинне живе клікабельне демо.

---

### Критерії оцінювання (максимум — 7 балів)
Оцінювання здійснюється за бінарною шкалою (1 бал — виконано, 0 балів — не виконано):

| № | Критерій | 1 бал | 0 балів |
|:---:|---|---|---|
| 1 | **Присутність команди** | Уся команда присутня на практичній зустрічі вчасно. | Відсутній хоча б один учасник команди (без поважної причини). |
| 2 | **Папка prompts/ (3 файли)** | Наявні всі 3 файли (`5.1`–`5.3`) з релевантними інженерними промптами під реалізацію та рев'ю. | Відсутній хоча б один файл, або тексти запитів шаблонні й не стосуються проєкту. |
| 3 | **Цілісність обраного сценарію** | Реалізовано один завершений користувацький флоу (наскрізний сценарій дає очікуваний результат). | Сценарій обривається на півдорозі, або реалізовано розрізнені, не пов'язані між собою елементи. |
| 4 | **Наскрізна робота з даними** | Дані проходять крізь систему та персистентно зберігаються (не зникають після перезапуску програми). | Дані захардкоджені в пам'яті інтерфейсу, не зберігаються в сховищі або база відсутня. |
| 5 | **Детермінована якість коду** | Проєкт успішно збирається; перевірка типів, компіляція та лінтери проходять без помилок. | Проєкт падає під час збірки, у консолі критичні помилки або порушено базову структуру коду. |
| 6 | **Код-рев'ю за допомогою ШІ** | Зміни влиті через Pull Request, де зафіксовано проведення перевірки коду штучним інтелектом. | Зміни закинуті напряму в `main` без PR, або сліди код-рев'ю від ШІ повністю відсутні. |
| 7 | **Живе клікабельне демо** | Команда наживо успішно продемонструвала роботу сценарію в інтерфейсі за відведений час (до 3 хв). | Демонстрація не відбулася, застосунок зламався під час показу, або показують лише статичний код у файлах. |
