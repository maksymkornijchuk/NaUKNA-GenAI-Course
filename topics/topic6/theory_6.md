# Тема 6. Робочий процес програміста з ШІ

# Вступ

**Після завершення цієї теми ви зможете:**

*   **Диференціювати** підходи до використання ШІ між середовищами розробки (IDE-акселератори) та консольними агентами (CLI-делегатори).
*   **Конфігурувати** кросплатформенний файл інструкцій `AGENTS.md` для запобігання прив'язці до одного вендора (Vendor Lock-in).
*   **Розробляти** повторювані скіли (Skills) та спеціалізованих агентів із розмежованими правами доступу (Permissions) для автоматизації інженерних обов'язків.
*   **Застосовувати** детерміновані інструменти перевірки (компілятори, лінтери, перевірку типів, автотести) як захисні бар'єри (Guardrails) проти стохастичних помилок моделі.
*   **Організовувати** багаторівневий процес код-рев'ю: від локального аудиту через ШІ-агента до автоматизованого аналізу в GitHub Pull Request.
*   **Впроваджувати** стандартизований чекліст готовності задачі (Definition of Done) під час реалізації користувацьких історій у командних репозиторіях.

### Парадигми інструментів: акселератори в IDE та делегатори в терміналі

Звичайні вебчати у браузері більше не відповідають вимогам професійної розробки: вони ізольовані від файлової системи, швидко втрачають контекст і вимагають постійного ручного копіювання коду. Сьогодні індустрія розділилася на два основні підходи до інтеграції ШІ у робочий процес:

1.  **IDE-асистенти / Акселератори (Cursor, GitHub Copilot, Windsurf):**
    *   Працюють безпосередньо у редакторі коду під час набору тексту.
    *   Спеціалізуються на контекстному автодоповненні, генерації окремих методів, швидких правках виділених фрагментів та відповідях на локальні запитання щодо відкритих файлів.
    *   *Роль інженера:* розробник самостійно веде процес написання коду рядок за рядком, а ШІ прискорює механічну роботу.
2.  **Термінальні агенти / Делегатори (Claude Code, Gemini CLI, Aider, Codex):**
    *   Працюють як самостійні консольні процеси з прямим доступом до файлової структури, терміналу та команд Git.
    *   Отримують комплексне завдання (наприклад, реалізувати готову User Story), самостійно знаходять релевантні файли, вносять правки, запускають перевірки типів і виконують тести для самоперевірки.
    *   *Роль інженера:* розробник делегує виконання завершеної задачі, контролює етапи планування та проводить прискіпливе рев'ю результатів.

Вибір інструмента залежить від задачі: для швидкого написання UI-компонентів чи точкових правок зручніші акселератори в IDE, тоді як для наскрізної реалізації бекенд-ендпоінтів, рефакторингу чи системних задач краще підходять CLI-агенти.

Розібравшись із вибором між IDE та терміналом, важливо налаштувати робоче середовище так, щоб не залежати від примх конкретного комерційного провайдера.

### Універсальна конфігурація: файл AGENTS.md проти прив'язки до вендора

ШІ-інструменти розвиваються дуже швидко: модель або плагін, які були лідерами ринку пів року тому, сьогодні можуть поступатися новим рішенням. Якщо прописувати інструкції та правила проєкту суто під одного вендора (наприклад, тільки у файлі `CLAUDE.md` для Claude або `.github/copilot-instructions.md` для GitHub Copilot), команда опиняється у пастці **Vendor Lock-in** — вимушеної залежності від конкретного сервісу.

Дублювати однакові тексти інструкцій у різні конфігураційні файли категорично не рекомендується: з часом у них неминуче виникнуть розбіжності та суперечності. 

Ефективним інженерним рішенням є створення **єдиного джерела правди** — файлу `AGENTS.md` у корені репозиторію. Усі вендоро-специфічні файли конфігурацій при цьому зводяться до короткої вказівки імпортувати базові правила:

```
[Файл AGENTS.md у корені репозиторію] ➔ Єдине джерело правил проєкту
        ▲
        ├── CLAUDE.md                   (містить директиву: import AGENTS.md)
        ├── .github/copilot-instructions.md (посилається на AGENTS.md)
        └── .cursorrules / .windsurfrules (посилаються на AGENTS.md)
```

#### Обов'язкова структура файлу `AGENTS.md`:
1.  **Опис системи (Project Overview):** призначення продукту в 1–2 реченнях (наприклад, суть сервісу DevMatch).
2.  **Стек і команди (Commands):** точні консольні команди для збірки, запуску dev-сервера, перевірки типів та прогону тестів (`pnpm dev`, `pnpm typecheck`, `pnpm test`).
3.  **Карта документації (Documentation Map):** прямі вказівки, які файли з папки `docs/` модель зобов'язана прочитати перед зміною схем бази даних, додаванням ендпоінтів чи роботою над користувацькими історіями.
4.  **Головне інженерне правило:** *«Не додумуй вимоги мовчки. Якщо інформація відсутня або суперечлива — зупинись і запитай людину»*.

Коли єдині правила проєкту зафіксовані, постає питання: як автоматизувати виконання типових інженерних завдань без необхідності щоразу вручну писати довгі запити?

### Анатомія скілів та агентів: алгоритми дій та обмеження прав

Постійне введення однакових тристорінкових промптів у термінал забирає час, призводить до помилок і швидко перевантажує контекстне вікно моделі. Для автоматизації повторюваних операцій використовують два взаємодоповнюючі інструменти: **Скіли (Skills)** та **Спеціалізовані агенти (Sub-agents)**.

```
+-------------------------------------------------------------------------+
|                  СКІЛ (Skill) проти АГЕНТА (Agent)                      |
+-------------------------------------------------------------------------+
| СКІЛ (наприклад, implement-story):                                      |
| • Чіткий покроковий алгоритм дій під конкретну команду                  |
| • Приймає динамічні аргументи (номер історії: US-01, US-06)             |
| • Завантажується в пам'ять моделі ТІЛЬКИ в момент виклику               |
|                                                                         |
| АГЕНТ (наприклад, architecture-reviewer):                               |
| • Окрема роль зі строго обмеженим набором інструментів (Permissions)    |
| • Працює в режимі Read-only (tools: read, grep, bash; БЕЗ write/edit)   |
| • Фізично не може змінити код — лише аналізує diff і формує звіт        |
+-------------------------------------------------------------------------+
```

#### Анатомія скіла `implement-story` (кейс DevMatch)
Скіл зберігається як звичайний файл Markdown (наприклад, `.claude/skills/implement-story/SKILL.md`). Коли розробник вводить у терміналі команду `/implement-story US-01`, агент виконує фіксовану послідовність кроків:
1.  Приймає номер історії (`US-01`) як вхідний аргумент.
2.  Знаходить файл `docs/US-01.md`, зчитує критерії прийняття (Acceptance Criteria) та сценарії Gherkin (Given-When-Then).
3.  Звіряється з матрицею простежуваності (`docs/architecture/traceability.md`), специфікацією API (`api.md`) та моделлю даних (`data-model.md`).
4.  **Обов'язкова зупинка:** формує покроковий план змін і очікує прямого підтвердження (Approve) від розробника.
5.  Після схвалення плану реалізує бізнес-логіку у відповідних пакетах (`apps/api`, `apps/web`, `packages/shared`).
6.  Запускає команду тестування і перевіряє зелений статус виконання.

#### Анатомія агента `architecture-reviewer`
Файл опису ролі (наприклад, `.claude/agents/architecture-reviewer.md`) містить інструкції для аудиту коду. Його ключова особливість — налаштування прав доступу: агент має доступ до читання файлів, пошуку та виконання неруйнівних команд, але йому **заборонено редагувати файли**. Він зіставляє поточний `git diff` із зафіксованими архітектурними рішеннями (ADR) і формує звіт про знайдені відхилення (наприклад, спробу написати валідацію в обхід `packages/shared` або прямий виклик бази даних із контролера).

Маючи готові скіли та агентів, важливо правильно керувати процесом їх запуску та захистити робоче середовище від випадкових пошкоджень.

### Режими взаємодії та безпека робочого простору в Git

Термінальні агенти підтримують кілька режимів роботи, які перемикаються гарячими клавішами (наприклад, `Shift + Tab`):

*   **Plan Mode (Режим планування / Read-only):** режим дослідження та проєктування. Агент сканує файли, з'ясовує залежності та пропонує план робіт. Будь-які зміни файлів на диску в цьому режимі заблоковані.
*   **Auto / Edit Mode (Режим виконання):** агент самостійно виконує дії за схваленим планом, створює файли та застосовує виправлення.

#### Правила безпеки в Git під час роботи з ШІ:
1.  **Правило чистого робочого дерева:** ніколи не запускайте агента в режимі редагування, якщо у вашому репозиторії є незбережені ручні правки (`git status` обов'язково має бути чистим). Якщо агент припуститься помилки та спробує виконати команду відкату (`git restore`), він може безповоротно стерти ваш код.
2.  **Ізоляція гілок і робочих просторів:** кожна окрема користувацька історія має розроблятися у власній Git-гілці (`feature/us-01`) або в окремому робочому просторі (Worktree: `claude -w us-01`). Якщо результат генерації виявиться невдалим, таку гілку можна просто видалити без ризику пошкодити основну гілку `main`.
3.  **Розмежування автодозволів:** дозволяйте агенту автоматично виконувати безпечні операції (читання файлів, запуск лінтерів, компіляцію, прогін тестів). Проте потенційно деструктивні дії (`git push`, `git reset`, операції видалення файлів) завжди мають вимагати ручного підтвердження людиною.

Безпечне середовище в Git створює надійні умови для переходу до безпосереднього написання коду без скочування у хаотичні експерименти.

### Інженерний процес проти «Vibe Coding»: детерміновані бар'єри

Головна небезпека так званого Vibe Coding полягає в ілюзії швидкості: розробник отримує працюючий інтерфейс, але не знає, як саме він влаштований. Модель може покласти критичні дані в локальний кеш браузера замість персистентного збереження в базі даних або приховати виняток, створивши вразливість, яка проявиться лише на етапі експлуатації.

Оскільки великі мовні моделі є **стохастичними (ймовірнісними)** системами, вони схильні щоразу генерувати дещо відмінний результат. Щоб змусити стохастичний інструмент працювати надійно, його поміщають усередину **детермінованих інженерних бар'єрів (Guardrails)** — автоматичних фільтрів, які працюють за суворими математичними правилами 10 разів із 10:

```
[Стохастичний ШІ генерує код]
             ↓
[1. Компілятор і Typescript (Typecheck)] ➔ Помилка типу? ➔ Відкат / Виправлення
             ↓
[2. Статичні лінтери (ESLint / Prettier)] ➔ Порушення стилю? ➔ Відкат / Виправлення
             ↓
[3. Автоматизовані тести (Vitest / JUnit)] ➔ Тест упав? ➔ Автономне виправлення коду
             ↓
[Код відповідає технічним контрактам]
```

#### Залізне правило інженерії: заборона редагувати тести
Якщо згенерований код не проходить автотести, у моделі виникає спокуса «виправити проблему» найпростішим шляхом — змінити сам файл тесту, щоб він повертав успішний статус. 

В інструкціях для ШІ обов'язково фіксується непорушне обмеження:
> **«Тобі суворо заборонено змінювати файли існуючих тестів. Модифікуй виключно код реалізації доти, доки всі тести не стануть зеленими».**

Коли код згенеровано крізь сито детермінованих перевірок, настає вирішальний етап — всебічний аудит та рев'ю результатів.

### Багаторівневе код-рев'ю: від локальних тестів до Pull Request

Фрази ШІ *«все готово, код працює ідеально»* абсолютно недостатньо для злиття змін у кодову базу. Перевірка результатів здійснюється у чотири послідовні етапи:

```
1. Детерміновані перевірки  ➔  2. Ручний Smoke Test  ➔  3. Локальний аудит ШІ  ➔  4. Рев'ю в Pull Request
   (typecheck, linter, tests)    (перевірка в браузері)    (агент architecture-reviewer)   (GitHub Copilot / Actions)
```

1.  **Детерміновані перевірки:** виконання команд `pnpm typecheck` та `pnpm test` у терміналі. Перевіряється коректність типів даних і проходження контрактних тестів.
2.  **Ручний смоук-тест (Manual Smoke Test):** розробник власноруч запускає застосунок у браузері (`pnpm dev`) і перевіряє роботу створеного екрана. Обов'язково перевіряються не лише успішні сценарії (Happy Path), а й граничні випадки (Edge Cases) — наприклад, спроба надіслати порожнє поле або ввести некоректний нікнейм Telegram.
3.  **Локальний аудит через ШІ-агента:** запуск сублімованого агента `architecture-reviewer` для перегляду `git diff`. Агент звіряє зміни з ADR-файлами та повідомляє про архітектурні порушення (наприклад, забутий `trim()` для рядків чи пряму передачу хешу пароля у відповіді API).
4.  **Автоматизоване рев'ю в Pull Request:** створення PR у GitHub, де підключені інструменти (GitHub Copilot for PRs або воркфлоу на базі GitHub Actions) автоматично аналізують зміни та залишають коментарі безпосередньо до рядків коду.

Процес верифікації коду логічно випливає із загального розподілу ролей між людиною та штучним інтелектом у сучасному проєкті.

### Триада розробки: проєктування, реалізація та валідація

Увесь життєвий цикл розробки будь-якого компонента складається з трьох ключових фаз:

```
[ 1. ПРОЄКТУВАННЯ ]   ➔   [ 2. РЕАЛІЗАЦІЯ ]   ➔   [ 3. ВАЛІДАЦІЯ ]
    (Людина + ШІ)             (Делеговано ШІ)          (Людина + ШІ)
  Фінальне рішення:          Генерація коду          Фінальне рішення:
       ЛЮДИНА                   в рамках                 ЛЮДИНА
```

*   **Проєктування (Design):** визначення вимог, вибір технологій, оцінка архітектурних компромісів (ADR), моделювання даних. ШІ залучається як спаринг-партнер для брейнштормінгу, але фінальне архітектурне рішення ухвалює виключно людина.
*   **Реалізація (Implementation):** написання boilerplate-коду, рутинних методів, верстка за макетами, створення тестів за Gherkin-сценаріями. Цей етап максимально делегується ШІ-агентам під контролем скілів.
*   **Валідація (Validation):** перевірка коду через тести, оцінка безпеки, аналіз ризиків і проведення рев'ю. ШІ допомагає шукати помилки, але остаточний підпис під Pull Request ставить інженер.

Цей розподіл обов'язків безпосередньо визначає, як молодому спеціалісту розвивати власні компетенції та не втрачати інженерну базу.

### Професійний розвиток інженера в еру генеративного ШІ

Працювати з ШІ-агентом найпростіше за аналогією з **управлінням віддаленим стажером**: йому потрібно давати вичерпні початкові інструкції, ставити чіткі межі та прискіпливо перевіряти кожен рядок виконаної ним роботи. Якщо ви не можете пояснити, як працює згенерована функція, чому обрано саме цей алгоритм і які обмеження він має, — ви не готові нести відповідальність за цей код.

#### Практичні поради для джуніорів:
*   **Зберігайте фундаментальні навички кодингу:** щоб розуміти, як проєктувати системи, корисно мати персональні тренувальні проєкти, де ви пишете код повністю вручну без генераторів (наприклад, написання базового HTTP-сервера за класичними підручниками). Це розвиває інженерну інтуїцію, без якої неможливо помітити тонкі архітектурні баги у згенерованому коді.
*   **Використовуйте ШІ як інтерактивного ментора:** замість прохання «напиши мені готову відповідь» використовуйте інструменти для глибокого навчання (наприклад, завантажуйте документацію чи книги в NotebookLM / Gemini, просіть модель пояснювати складні концепції через аналогії, генерувати контрольні квізи та ставити вам підступні запитання).
*   **Розвивайте навички роботи в команді:** індустріальні проєкти ніколи не створюються наодинці; здатність домовлятися про контракти, аргументувати власні технічні рішення та брати на себе відповідальність за результат залишається головною конкурентною перевагою на ринку праці.

Щоб закріпити ці принципи у щоденній командній роботі, зафіксуємо підсумковий критерій готовності будь-якої задачі.

### Чек-лист виконання користувацької історії (Definition of Done)

Команда вважає обрану User Story повністю завершеною лише за умови виконання наступних пунктів:

* [ ] Для задачі створено окрему гілку в Git (`feature/us-xx`) за умови чистого робочого дерева.
* [ ] Запущено відповідний скіл (наприклад, `/implement-story US-xx`) у режимі планування (**Plan Mode**), покроковий план змін узгоджено розробником.
* [ ] Код реалізовано строго в межах архітектурних контрактів без самовільної модифікації сторонніх файлів.
* [ ] Перевірка типів (`pnpm typecheck`) та лінтери проходять без жодної помилки.
* [ ] Усі автоматичні тести виконуються успішно, при цьому самі файли тестів ШІ не редагував.
* [ ] Працездатність сценарію перевірена вручну в інтерфейсі (успішний сценарій та обробка некоректного введення).
* [ ] Переглянуто локальний `git diff`, запущено агента `architecture-reviewer`, усунуто тимчасові файли та зауваження.
* [ ] Створено Pull Request у GitHub, автоматичне код-рев'ю пройдено без блокуючих зауважень.
* [ ] Зміни успішно змерджено в гілку `main`.

### Підсумки

Генеративний штучний інтелект докорінно змінює щоденну рутину програміста, беручи на себе механічне написання синтаксису. Проте справжня інженерна цінність полягає не в швидкості набору коду, а в здатності структурувати вимоги, будувати захисні детерміновані бар'єри та керувати автономними агентами через прозорі правила й контракти.

**Ключові опорні точки теми:**

*   **Інструменти за призначенням:** використання IDE-асистентів як акселераторів для швидкого написання коду та CLI-агентів як автономних делегаторів для виконання комплексних задач.
*   **Універсальність `AGENTS.md`:** налаштування єдиного файлу інструкцій усуває прив'язку до одного комерційного вендора та стандартизує роботу команди.
*   **Скіли та права доступу:** автоматизація розробки через кастомні алгоритми (Skills) та спеціалізованих агентів (Agents) із правами Read-only для безпечного аудиту коду.
*   **Детерміновані бар'єри проти Vibe Coding:** контроль стохастичного ШІ через сувору типізацію, лінтери та автотести, із непорушною забороною для моделі змінювати перевірочні тести.
*   **Відповідальність інженера:** делегування етапу реалізації за умови повного збереження контролю над проєктуванням, валідацією та схваленням кожного рядка в Pull Request.

Застосуйте скіл `/implement-story` для реалізації вашої чергової користувацької історії у репозиторії, провалідуйте результат крізь детерміновані тести та проведіть повне код-рев'ю перед створенням Pull Request. А вже на наступній лекційній зустрічі ми зануримося у професійні практики тестування та дослідимо, як QA-інженери використовують ШІ для забезпечення бездоганної якості програмних систем.
