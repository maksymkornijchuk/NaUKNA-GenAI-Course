# Тема 6. Робочий процес програміста з ШІ

---

### 1. IDE чи термінал: два підходи до роботи з ШІ

* **Суть простими словами:** Чати в браузері більше не використовуються для написання коду. Сучасна розробка розділилася на два формати: ШІ всередині редактора коду або ШІ в терміналі.
* **Асистент в IDE (Cursor, GitHub Copilot):**
  * Працює прямо у файлі, де ви пишете код.
  * Допомагає дописувати рядки (автодоповнення), генерує окремі методи та пояснює виділений фрагмент.
  * Ви самі ведете процес, а ШІ прискорює набір синтаксису.
* **Термінальний агент (Claude Code, Gemini CLI):**
  * Працює в консолі та має доступ до файлової системи й терміналу.
  * Отримує комплексне завдання (наприклад, реалізувати User Story), сам шукає потрібні файли, змінює код і перевіряє себе через запуск тестів.
  * Виступає автономним виконавцем, результат якого ви перевіряєте.

### 2. Файл AGENTS.md: єдині правила для ШІ

* **Проблема прив'язки до одного вендора:**
  * Якщо прописати правила проєкту суто для Claude у файлі `CLAUDE.md`, то за потреби використати Gemini чи Copilot доведеться все налаштовувати заново.
  * Дублювати однаковий текст у різні файли конфігурацій не можна — вони швидко стануть суперечливими.
* **Рішення — універсальний `AGENTS.md`:**
  * Створюється один головний файл інструкцій у корені проєкту — `AGENTS.md`.
  * Будь-які інші системні файли (як-от `CLAUDE.md`) містять лише одне речення: посилання на `AGENTS.md`.
* **Що має бути в `AGENTS.md`:**
  1. **Короткий опис проєкту:** Суть системи в 1–2 реченнях (кейс DevMatch).
  2. **Команди запуску та перевірки:** Як запустити dev-сервер, як перевірити типи та запустити тести (`pnpm test` / `mvn test`).
  3. **Карта документації:** Які файли з папки `docs/` модель має прочитати перед створенням ендпоінта чи зміною бази даних.
  4. **Головне правило:** *«Не додумуй вимоги мовчки. Якщо чогось немає в документації — запитай розробника»*.

### 3. Скіли та агенти: автоматизація задач і ролей

* **Чому це не «просто промпти»:**
  * Якщо щоразу писати моделі велику інструкцію на 3 сторінки в чат, ви витрачаєте час, забуваєте важливі обмеження, а модель з часом «деградує» через перевантаження пам'яті.
  * Замість цього повторювані інструкції оформлюють як **Скіли (Skills)**, а спеціалізовані обов'язки — як **Агентів (Agents)**.

#### Що таке Скіл (Skill) під капотом
* **Фізична сутність:** Це звичайний текстовий файл (`SKILL.md`), який лежить у репозиторії (наприклад, `.claude/skills/implement-story/SKILL.md`).
* **Як він працює:** Це заздалегідь написаний чіткий алгоритм дій. Коли ви пишете коротку команду `/implement-story US-01`, агент підвантажує цей файл як суворе керівництво.
* **Анатомія скіла `implement-story` (кейс DevMatch):**
  1. Прийняти аргумент (номер історії, наприклад `US-01`).
  2. Знайти відповідний файл у `docs/US-01.md`, прочитати Acceptance Criteria та Gherkin.
  3. Звіритися з `docs/architecture/api.md` та моделлю даних.
  4. **Обов'язкова зупинка:** Скласти план змін і чекати підтвердження від людини.
  5. Написати код фічі за планом.
  6. Запустити тести.

#### Що таке Агент (Agent) під капотом
* **Фізична сутність:** Це файл опису ролі (наприклад, `.claude/agents/architecture-reviewer.md`), де зафіксовано **персону** та **жорсткі технічні обмеження (Permissions)**.
* **Головна відмінність від скіла — права доступу:**
  * Звичайний агент має право редагувати файли (`write`).
  * Спеціалізований агент-рев'юер має права: `tools: read, grep, bash`, але **не має доступу до `edit / write`**.
  * Він фізично не здатен змінити жодного рядка вашого коду — він може лише переглянути `git diff`, звірити його з архітектурними рішеннями (ADR) і написати вам звіт про помилки.

#### Чому це критично для проєкту
* **Економія пам'яті моделі:** Скіл завантажується в контекст лише в момент виклику, а не висить у пам'яті постійно.
* **Передбачуваність:** Кожна User Story в команді розробляється за єдиним чітким стандартом.

### 4. Режими роботи: планування, виконання та захист Git

* **Режими взаємодії з агентом:**
  * **Plan Mode (Shift + Tab):** Режим «тільки для читання». Агент сканує проєкт, з'ясовує залежності та показує покроковий план. Файли на диску не змінюються, доки ви не підтвердите план.
  * **Auto / Edit Mode:** Режим виконання. Агент вносить зміни у файли за узгодженим планом.
* **Безпека робочого простору в Git:**
  * **Правило чистого дерева:** Ніколи не запускайте агента в Auto Mode, якщо у вас є незбережені ручні зміни (`git status` має бути чистим).
  * Якщо агент помилиться або спробує виконати відкат через `git restore`, він може стерти ваші власні правки.
  * **Ізоляція гілок:** Кожна окрема історія робиться в окремій гілці (`git checkout -b feature/us-01`). Якщо результат невдалий — гілку можна просто видалити й спробувати ще раз.

### 5. Написання коду: інженерія замість Vibe Coding

* **Пастка Vibe Coding:**
  * Спроба писати код методом «натискай Enter у чаті, доки не перестане падати помилка». У результаті з'являється незрозумілий код, який неможливо підтримувати.
* **Стохастичний ШІ та детерміновані бар'єри (Guardrails):**
  * ШІ — ймовірнісний інструмент (може видавати різний результат або лінуватися).
  * Щоб гарантувати якість, код пропускають крізь жорсткі фільтри, які завжди працюють однаково:
    1. **Перевірка типів і компілятор:** не дозволяють звертатися до неіснуючих полів.
    2. **Лінтери:** вимагають чистоти коду та однакового форматування.
    3. **Автоматичні тести:** перевіряють виконання бізнес-правил.
* **Головне інженерне обмеження: заборона чіпати тести!**
  * Якщо агент написав код, запустив тест і той «упав», модель може спробувати схитрувати — переписати тест так, щоб він став зеленим.
  * *Суворе правило в інструкціях для ШІ:*  
    > **«Тобі суворо заборонено змінювати файли існуючих тестів. Виправляй код реалізації доти, доки тести не пройдуть успішно».**

### 6. Код-рев'ю: локальна перевірка та GitHub Pull Request

* **Чому фрази «все працює» недостатньо:**
  * ШІ може написати код, який працює на вашому комп'ютері, але ламає логіку для інших користувачів або зберігає паролі у незахищеному вигляді.
* **Чотири етапи перевірки:**
  1. **Детерміновані перевірки:** Прогон лінтера, перевірки типів і тестів у терміналі.
  2. **Ручний перегляд (Smoke Test):** Власноруч запустити додаток і перевірити його роботу в браузері (обов'язково перевірити сценарій із помилкою введення).
  3. **Локальний аудит ШІ:** Запуск агента `architecture-reviewer`, щоб перевірити `git diff` на відповідність домовленостям.
  4. **Автоматичне рев'ю в Pull Request:** Автоматичний аналіз змін у GitHub (через GitHub Copilot або GitHub Actions), який залишає зауваження до рядків коду перед злиттям.
* **Відповідальність розробника:**
  * За кожен змерджений рядок коду відповідає людина, яка затвердила Pull Request, а не ШІ.
  * Якщо ви не можете пояснити, що робить написаний код — ви не маєте права відправляти його в `main`.

### 7. Чекліст виконання задачі (Definition of Done)

Команда вважає обрану User Story повністю готовою, якщо виконано такі кроки:

* [ ] Створено окрему гілку в Git під задачу.
* [ ] Запущено скіл у режимі планування (**Plan Mode**), план дій узгоджено людиною.
* [ ] Код реалізовано без зміни сторонніх файлів проєкту.
* [ ] Перевірка типів і лінтер проходять без помилок.
* [ ] Усі тести проходять успішно, при цьому самі файли тестів ШІ не редагував.
* [ ] Працездатність сценарію перевірено вручну в інтерфейсі (успіх та обробка помилки).
* [ ] Переглянуто `git diff`, прибрано зайвий код і тимчасові файли.
* [ ] Створено Pull Request у GitHub, код пройшов автоматичне рев'ю без блокуючих зауважень.
* [ ] Зміни змерджено в гілку `main`.
