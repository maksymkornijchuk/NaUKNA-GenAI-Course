# Концепція Практичного завдання №5

## 1. Інженерне позиціонування завдання (Де ми знаходимося)

* **Попередня точка (КТ-4):** У команд є живий «крокуючий скелет» (порожній проєкт, що запускається, має контракти, схему бази даних та налаштований `CLAUDE.md` або правила для асистента).
* **Поточна точка (КТ-5):** **«Розробка: перший робочий сценарій»**. Команди вперше вдихають життя в систему за допомогою ШІ-інструментів безпосередньо в IDE.
* **Головна мета:** Реалізувати **один наскрізний користувацький сценарій (Vertical Slice)** через усі рівні (UI ➔ Backend ➔ DB) із реальними даними. 
* **Критична межа:** Команда **не повинна** намагатися закодити весь беклог чи всі 10 історій! Потрібно взяти **одну ключову історію** (або один зв'язний ланцюжок дій), написати під неї код за допомогою ШІ, зробити AI-рев'ю, зачистити технічний борг і показати, що дані реально зберігаються й відображаються.

---

## 2. Що конкретно має зробити студентська команда (4 кроки)

1. **Обрати перший наскрізний сценарій (Vertical Slice):**
   * Обрати із затвердженого MVP **одну головну дію користувача**, яка дає відчутний результат (наприклад, для *DevMatch*: «Створення проєкту з вакансіями» або «Подача заявки з відображенням у списку лідера»).
   * Цей сценарій має пройти крізь усі 3 шари: екран введення/перегляду (UI) ➔ виклик сервера (API) ➔ збереження/читання з бази даних (DB).

2. **Реалізувати код фічі за допомогою ШІ в IDE:**
   * Використати обраний командою асистент (Claude Code, GitHub Copilot, Cursor, JetBrains AI тощо).
   * **Правильно завантажити контекст у ШІ:** передати моделі відповідну User Story з критеріями прийняття (КТ-3), схему бази даних та специфікацію API (КТ-4).
   * Згенерувати реалізацію пошарово: міграції/моделі БД ➔ бізнес-сервіс та ендпоінт ➔ UI-компоненти з обробкою станів (завантаження, успіх, помилка).

3. **Провести перевірку та покращення коду за допомогою ШІ (AI Review & Refactoring):**
   * Сформулювати промпт для аудиту створеного коду (в IDE або як рев'ю пулл-реквесту):
     * *Чи не порушено архітектуру?* (наприклад, бізнес-логіка не повинна лежати прямо в компонентах UI чи в контролерах).
     * *Чи відповідає відповідь API узгодженому контракту?*
     * *Чи обробляються помилки валідації?*
   * За допомогою ШІ провести рефакторинг: спростити заплутані місця, прибрати зайвий або згенерований небезпечний код («нейрослоп»).

4. **Зафіксувати подолані блокери:**
   * Коротко описати 1–2 випадки, де ШІ «нагаллюцинував» (наприклад, використав застарілий синтаксис, вигадав неіснуючу функцію бібліотеки чи порушив контракт) і як команда це виправила.

## 3. Що має бути здано в репозиторії (Артефакти)

1. **Працюючий код першого сценарію:**
   * Зміни збережені у репозиторії (бажано через Pull Request, де видно історію змін).
   * Застосунок успішно запускається локально, екран сценарію доступний для взаємодії.
2. **Короткий звіт у `docs/first-feature.md` (або оновлення `README.md`):**
   * Назва реалізованої історії/сценарію.
   * Інструкція: як саме клікнути/перевірити цей сценарій під час запуску (наприклад: *«Перейти на /projects/new ➔ заповнити форму ➔ натиснути "Створити" ➔ переконатися, що проєкт з'явився в списку на головній»*).
   * 2–3 речення про те, з якими проблемами від ШІ зіткнулися під час кодогенерації та як їх вирішили.
3. **Папка `prompts/` (3 нові файли):**
   * `5.1_code_generation.md` — промпт із передачею контексту для генерації коду (сервіс, контролер або UI).
   * `5.2_code_review.md` — промпт, яким проганяли написаний код на наявність багів, порушень архітектури та безпеки.
   * `5.3_refactoring.md` — промпт для рефакторингу й чистки коду від зайвих галюцинацій моделі.
4. **DistEdu:** посилання на репозиторій (або конкретний PR) у полі відповіді до дедлайну.

## 4. Регламент практичної зустрічі (20 хвилин)

* **Перші 3 хвилини — Live Demo (Студенти показують екран):**
  * Жодних слайдів чи довгих вступів.
  * Студент відкриває термінал / IDE, запускає проєкт.
  * У відкритому інтерфейсі наживо виконує дію (наприклад, вводить дані у форму та відправляє).
  * Показує результат: повідомлення про успіх в інтерфейсі + збережений запис у базі даних (через термінал, адмінку БД чи оновлену таблицю на сторінці).
* **Решта 17 хвилин — Інженерне рев'ю коду з викладачем:**
  * Викладач дивиться у код: *«Де тут бізнес-логіка? Чому обрали таку структуру? Як контролювали контекст у ШІ?»*.
  * Команда показує свій Pull Request та результати рефакторингу.
  * Викладач підказує, які слабкі місця треба виправити перед масовим написанням решти історій.

## 5. Концепція критеріїв оцінювання (максимум — 7 балів)

Критерії бінарні, прозорі та оцінюють реальний інженерний результат:

| № | Критерій | 1 бал | 0 балів |
|:---:|---|---|---|
| **1** | **Присутність команди** | Уся команда присутня на зустрічі вчасно. | Відсутній хоча б один учасник команди (без поважної причини). |
| **2** | **Папка `prompts/` (3 файли)** | Наявні файли `5.1`–`5.3` з релевантними промптами для генерації, перевірки (review) та рефакторингу коду. | Файли відсутні або містять примітивні абстрактні запити без інженерного контексту. |
| **3** | **Наскрізність сценарію (Vertical Slice)** | Реалізований функціонал зв'язує всі 3 рівні: дія в UI викликає API, а дані реально читаються/записуються в БД (не захардкоджені моки). | Сценарій «розірваний»: є тільки візуальна форма без бекенду або тільки API без можливості взаємодії через UI, чи дані зникають після перезавантаження. |
| **4** | **Дотримання контрактів (КТ-4)** | Ендпоінти, формат даних і поля в базі відповідають специфікаціям, спроєктованим на попередньому етапі. | Код повністю ігнорує попередні контракти (ШІ вигадав інші назви полів, методів або URL). |
| **5** | **Розділення відповідальності (Архітектура)** | Код логічно структурований: бізнес-правила винесені в сервісний шар, UI відповідає за відображення, відсутні грубі звалища коду «все в одному файлі». | Архітектура зламана: уся логіка запхана прямо в обробник кнопки інтерфейсу чи в один велетенський файл-контролер. |
| **6** | **Сліди рев'ю та рефакторингу** | У репозиторії є свідчення осмисленої роботи над кодом: історія комітів/PR або зафіксовані в звіті виправлення помилок, знайдених за допомогою ШІ. | Код виглядає як «сліпе» копіювання першої-ліпшої генерації ШІ без спроб його покращити чи почистити. |
| **7** | **Живе демо сценарію (до 3 хв)** | Команда наживо успішно продемонструвала роботу сценарію від початку до кінця за перші 3 хвилини зустрічі. | Демо провалилося: проєкт зламався під час показу, або команда не змогла продемонструвати наскрізну дію. |

---

### Чому ця концепція ідеальна для КТ-5:

1. **Знімає стрес перевантаження:** Студенти не намагаються зробити все. Вони роблять **один тонкий вертикальний зріз**, але якісно. Це доводить життєздатність стеку.
2. **Фокус на реальній роботі в IDE:** Завдання змушує студентів налаштувати свій робочий процес (годувати асистенту документацію з `docs/`, а не просто чатитися у вакуумі).
3. **Легка та видовищна перевірка для викладача:** На перших хвилинах ви бачите працюючий функціонал на екрані, а решту часу витрачаєте на якісний Code Review та менторство.
